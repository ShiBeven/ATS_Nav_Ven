# CAN2 通信堵塞静态检查（2026-10-29）

检查工程：`D:\code-ai\双板通信的云台`。本次检查当前源码与工程自带 HAL，不修改固件，不编译、烧录或操作硬件。无法由磁盘源码确认板上实际运行版本，也没有现场总线抓包。

## 结论

1. 已使用的 CAN2 发送路径没有等待邮箱腾空的 while 循环；HAL_CAN_AddTxMessage 只尝试提交邮箱并立即返回，因此未发现由 CAN2 发送等待直接卡死 CPU 的路径。
2. 本板名义周期发送合计约 740 帧/秒，1 Mbps 下估算占用约 8.2%～10.0%。本板发送量本身不支持“带宽已打满”的判断；其他节点发送、错误帧等尚未计入。
3. 存在静默丢帧、任务/中断并发提交、共享帧头被中断改写、接收 FIFO 溢出及 Bus-Off 后缺少恢复的风险。因此不能回答为“肯定不会堵”，也不能直接认定目前已发生拥堵。

## 时钟与名义发送量

源码：Src/main.c 的 HSE/PLL/APB1 配置、Inc/stm32f4xx_hal_conf.h 的 HSE_VALUE、Src/can.c:73、Src/tim.c:134 和 :345。

- HSE 12 MHz，PLL M=6/N=168/P=2，SYSCLK=168 MHz，APB1=42 MHz。
- CAN2：42 MHz / 3 / (1+10+3) = 1 Mbps。
- APB1 定时器时钟 84 MHz；TIM2：84 MHz / 168 / 1000 = 500 Hz，即每 2 ms 一次。
- TIM6：84 MHz / 1050 / 4000 = 20 Hz，即每 50 ms 一次。
- TIM2 的 20 槽循环实际是 40 ms；代码注释写 20 ms，与配置不符。

| 路径 | 标准帧 ID | 名义尝试频率 |
|---|---|---:|
| TIM2 偶数次，大 Yaw 驱动指令 | 0x1FF | 250 Hz |
| TIM2 奇数次，达妙陀螺仪请求 | 0x030 | 250 Hz |
| TIM2 槽 0，遥控基础 | 0x111 | 25 Hz |
| TIM2 槽 2，遥控辅助 | 0x112 | 25 Hz |
| TIM2 槽 4，鼠标 | 0x120 | 25 Hz |
| TIM2 槽 8，导航速度 | 0x113 | 25 Hz |
| USB 任务每至少 10 ms，导航速度 | 0x113 | 约 100 Hz |
| TIM6，编码器状态 | 0x121 | 20 Hz |
| TIM6，视觉状态 | 0x115 | 20 Hz |
| 合计 | | 约 740 帧/秒 |

当前 application/usb_task.h:26 为 USB_YAW_DEBUG=0，USB 导航发送路径有效，不能沿用历史调试宏为 1 时的结论。任务实际频率受调度影响，尝试次数不等于发送完成次数。

按每个标准 8 字节 CAN 数据帧约 111～135 bit（含帧间隔，填充位因数据而异）估算：740×(111～135)/1e6≈8.2%～10.0%。若达妙每次请求回复一帧，再加约 2.8%～3.4%；若大 Yaw 反馈另有 1000 Hz，再加约 11.1%～13.5%。这两项仅为明确假设下的计算，未测得实际回复率、电机反馈率或整网流量。

小 Yaw、Pitch 与发射机构的实际发送函数使用 hcan1，不计入 CAN2；不能只根据 CAN_receive.h 的 SHOOT_CAN 宏判断实际走线。

## 已发现的风险

### 1. 满邮箱时直接跳过，未统计

application/CAN_receive.c:234 的 gimbal_send_one_axis 检查空闲邮箱；没有空闲就直接返回，HAL 入邮箱结果也被忽略。components/devices/dm_imu.c:77 返回 HAL_BUSY/HAL_ERROR，但 imu_read_reg 等上层没有保留结果。板间发送函数同样忽略 HAL 返回值。

所以出现“程序继续跑，但某次命令或 IMU 请求没发出去”是可能的。HAL_OK 也只说明已提交邮箱，不能等同线上发送成功。

### 2. 短时发送集中，即使平均负载低也可能满邮箱

TIM2 的遥控/导航槽与大 Yaw 发送可能在同一次回调提交两帧；TIM6 一次回调也连续提交两帧。若两个定时器到期相近，且第 4 次提交前硬件未释放邮箱，就可能超过 3 个发送邮箱的即时容量。USB 任务还会提交 0x113。

这是条件性风险，未测得两定时器相位、邮箱驻留时间或实际满邮箱次数，不能称为已发生的周期性丢帧。

### 3. USB 与中断共用帧头，提交过程缺少统一并发保护

application/CAN_receive.c:126 的静态 board_tx_message 被 CAN_CmdBoard3、CAN_SendRcFrame、CAN_SendGimbalState、CAN_CmdBoard5 共用。CAN_CmdBoard3 在 USB 任务和 TIM2 中都调用。TIM2/TIM6 优先级均为 3，可以打断 USB 任务。

USB 准备 0x113 或进入 HAL 期间被定时中断打断，中断可能改写公共帧头；USB 恢复后可能使用被修改的 ID。导航缓冲 nav_data/nav_send_data 也被同一函数的任务和中断调用共享。

工程自带 HAL_CAN_AddTxMessage 在读 TSR、选择邮箱、写帧头/数据、置发送请求之间没有加锁。USB 任务被另一发送入口打断时还可能基于过期邮箱快照继续写邮箱。大 Yaw 的 gimbal_send_one_axis 自身有临界区，但不能保护其他未加保护的调用被其抢占前已开始的提交过程。

因此应同时解决共享打包缓冲与完整邮箱提交的并发问题，仅给某一个发送函数加保护不足以覆盖全部路径。TIM2 与 TIM6 抢占优先级相同，不应误述为它们互相抢占。

### 4. 0x113 重复发送，遥控发送源需按实物核实

0x113 同时由 USB 任务约 100 Hz 和 TIM2 25 Hz 发送，存在重复入口；增加约 25 帧/秒本身不是带宽打满的证据，但增加了共享状态及并发风险。

Src/bsp_pid.c 中“遥控统一由导航板广播”的注释与当前仍发送 0x111/0x112/0x120 的代码不一致。main.c 实际启动了本地 USART3 DBUS，同时保留 CAN 遥控接收兼容。若外部板也在相同物理 CAN2 上发送同 ID，需确认唯一数据源，不能仅凭注释宣称当前已经存在节点冲突。

### 5. 接收和故障恢复观测不足

bsp/boards/bsp_can.c 全 ID 放行到 FIFO0，只开启消息待处理中断；CAN2 RX 中断优先级 6，低于上述定时中断。接收回调每次取一帧，后续待收帧可再次触发中断，这本身不意味着永久积压；但中断长期得不到服务或突发接收过多时可能溢出。FIFO0 只有 3 帧容量，当前没有溢出累计。

Src/can.c:80/:82 关闭 AutoBusOff 和 AutoRetransmission；应用中未找到 CAN2 Bus-Off 恢复流程。不能以“本 MCU 自动无限重发”解释拥堵；但一旦进入 Bus-Off，也不能期待现有应用自动恢复。

## 如何确认现场是否真的堵塞

优先用 CAN 分析仪记录同一段工作状态下的总线占用、错误帧、各 ID 实际频率与最大间隔，重点看 0x030/0x031、0x1FF、0x113 和遥控帧。

现有 Keil Watch 可读取：

```c
(hcan2.Instance->ESR >> 16) & 0xFF  // TEC
(hcan2.Instance->ESR >> 24) & 0xFF  // REC
(hcan2.Instance->ESR >> 2) & 1      // BOFF
(hcan2.Instance->TSR >> 26) & 7    // 3 个邮箱的空闲位，0 表示全满
dm_gyro_age_ms
dm_gyro_online
dm_fault_latched
```

TSR 单次读到 0 不能证明长期堵塞，ESR 错误计数为 0 也不能排除软件丢帧。FIFO 溢出标志可能被 HAL 中断清除，不能只凭偶尔读取寄存器排除溢出。不要在 Watch 中调用有副作用的 HAL 函数。

若后续实施修改，优先加入每条总线的满邮箱、提交失败、完成、仲裁丢失/发送错误和接收溢出计数，再统一发送入口、使用独立打包缓冲、错开时隙。控制指令保留最新值，故障/停机时使旧输出失效，避免排长队后重放旧驱动指令。当前没有新增这些统计变量，不能要求读取不存在的变量。
