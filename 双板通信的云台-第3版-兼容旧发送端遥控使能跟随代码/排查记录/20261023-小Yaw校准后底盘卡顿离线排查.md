**离线检查没有定位到一个已证实导致本次卡顿的唯一根因。可以确认当前左下右中控制路径不使用大小Yaw校准角；不能据此排除通信、供电和机械耦合等间接影响。**

## 1. 校准角不会直接参与当前模式的底盘运动计算

- 底盘application/chassis_task.c的GetChassisMode：左下右中选择CHASSIS_FOLLOW_CHASSIS_YAW，枚举值3。
- ChassisFollowChassis从RC通道计算vx/vy/wz，经过斜坡、舵轮运动学、PID和功率限制。
- 该函数不使用RCData.gimbal_angle、RCData.yaw_ecd或云台gimbal_cali_valid。
- 因而，在实际运行确实为模式3的前提下，不能用“小Yaw校准后的零位直接改变底盘坐标变换”解释本次卡顿。
- 双中默认底盘STOP是当前底盘源码已有分支；不能将云台双中进入正常模式等同于底盘也进入运动模式。

## 3. 明确存在的通信时序隐患

云台Src/bsp_pid.c的遥控调度注释称20ms，实际TIM2频率为500Hz：

```text
HSE = 12MHz
SYSCLK = 12MHz / 6 * 168 / 2 = 168MHz
APB1 = 42MHz，定时器输入时钟 = 84MHz
TIM2 = 84MHz / 168 / 1000 = 500Hz
20个TIM2槽位 = 40ms
```

所以基本遥控帧0x111正常发送请求间隔为40ms，频率25Hz。0x112、0x120和0x113各自同样每40ms被调度一次。这里是软件请求频率，物理成功发送频率未测量。

底盘ChassisDataUpdate在基本帧接收年龄大于100ms时：

1. 清ch0/ch1/ch2；
2. 两拨杆置下；
3. 本周期GetChassisMode返回STOP；
4. ChassisStop清驱动和舵向软件输出。

若持续恢复接收又反复超时，能够产生反复停止。正常40ms更新本身不会触发100ms保护；例如连续丢失两次40ms更新时，两次成功接收相隔120ms，才会出现短时超时窗口。不能把“存在隐患”写成“已经证明本次持续丢帧”。

当前CAN_SendRcFrame忽略HAL_CAN_AddTxMessage返回值，没有成功/失败计数和重试队列。邮箱满或发送异常可能丢掉某次请求，但本轮没有实际失败证据。

上述时序也存在于现存小Yaw限位校准副本；校准前CAN发送函数体同样不检查返回值。本轮没有证据证明40ms时序或这项遗漏由小Yaw校准修改引入。因此仅凭该发现，不能宣称已找到了此次回归的根因，也不应直接放宽底盘超时保护。

## 4. 其他已核对事项

- 小Yaw校准新增了电机反馈时间戳、一致性快照、校准状态门控及完整独立电机报文提交。关中断片段没有源码上的100ms延时或等待循环，不能仅凭有__disable_irq就断言它造成遥控超时；真实执行时长没有测量。
- 当前云台Src/bsp_pid.c的大Yaw发送调用已被注释。与小Yaw限位校准副本相比，该文件唯一差异是这处注释。本轮保留，未擅自恢复。停止发送不等于主动发送零输出。
- 历史已确认大Yaw CAN2与Pitch CAN1物理独立；底盘电机用自身CAN1，板间用CAN2。不能只因两板都出现0x205就认定ID冲突。
- 历史“大Yaw断动力后Pitch恢复正常”的证据仅针对Pitch，不能代替“底盘卡顿也恢复”的对照。供电/共地/干扰或机械受力对底盘的影响仍未确认。
- 只有GYR校准流程调用RC_unable，约20秒后RC_restart；机械Pitch+小Yaw校准不通过这个宏关闭遥控。这是既有GYR流程，不能把机械校准与IMU零偏校准混为一谈。
- USB_YAW_DEBUG=1关闭常规USB导航接收，是当前工程既有设置。它会影响导航控制，但不直接解释此前左下右中由RC输入的模式3卡顿。
- D:/code-ai/底盘-第2版与当前桌面底盘的CAN_receive.c、chassis_power_control.c、chassis_task.h和bsp_tim.c相同；chassis_task.c仅小陀螺ChassisTop的通道/符号不同。这不改变模式3的上述分析。
- 底盘RC比例0.02、斜坡frame_period=0.1而任务osDelay(1)、旋转输出乘10均是既有疑点；没有实际指令和反馈时，不调整这些参数掩盖问题。

## 5. 暂无车辆时的处理边界

本轮不改Yaw/Pitch PID、底盘运动参数或安全超时，不要求用户接车、重新校准、回刷或复现抖动。保留当前固件与修改，避免混入新变量。

后续具备条件时，首先区分输入链路和轮组输出：底盘模式3是否稳定、0x111接收年龄是否超过100ms、RC通道是否连续。模式/输入异常先查云台DBUS到板间CAN；模式和输入连续但仍卡顿，再查底盘速度目标、轮组反馈、输出及电源。若需对比旧固件，应先确认版本、参数兼容和校准行为，不能让旧版上电校准造成意外动作。

**本次交付是离线排查记录，不是已经实车验证的修复。**

## 6. 后续分步测试单

用户目前无法接车。本清单供具备连接条件后执行；现在只需准备调试项，不要求立即进行。

1. 使用与板上固件对应的调试符号，先接底盘板。保留当前版本，不为测试改PID、重做校准或回刷旧固件。观察期间保持Run，不打断点；暂停会改变通信与运动状态。
2. 第一轮只给两块控制板和遥控接收机供电，先关闭电机动力，保留板间CAN。初始双下，随后左下右中，小幅推动一个平移摇杆约2秒、回中，重复三次。断动力轮组不动是预期结果；本轮只检查软件请求和通信。
3. 底盘Watch准备ChassisData.ChassisMode、uwTick - rc_basic_last_tick、RCData.rc.ch[0]、[1]、[2]及ChassisData.VxSet、Vyset、Wzset。接收年龄用十进制毫秒读取；正常发送请求间隔40ms，实际接收年龄通常约0～40ms加少量延迟。默认左下右中应稳定模式3；输入随摇杆变化且持续保持。双下应模式0。
4. 若年龄跨100ms且模式3/0反复变化、通道被清零，确认发生基本遥控接收超时，再沿云台接收与板间发送/接收定位。若年龄正常但模式错，先核实两拨杆字段和实际档位，不能称CAN超时。若模式3、输入连续但速度请求异常，再查RC映射/斜坡。
5. 注意ChassisStop只清电流输出，不清VxSet等速度变量；STOP时看到非零VxSet可能是旧值，不能据此认定底盘仍在主动驱动。Watch各项刷新不同步且可能漏掉短时异常，一次正常截图不足以排除偶发超时。
6. 第一轮输入稳定后，可靠架起底盘使轮组悬空、云台避开限位，再恢复电机动力，重复同样小输入。若只在有动力时卡顿，记录模式/接收年龄是否同时异常；输入和目标保持正常时，再看MotorWheel、MotorRudder及give_wheelCurrent/give_RudderCurrent，区分反馈、控制输出、动力与机械问题。架空正常不保证落地负载正常。
7. 若第一轮已有超时，再切换调试连接到云台板，看uwTick - rc_last_can_tick、rc_ctrl.rc.ch及拨杆。云台输入也断则查接收机/本地DBUS或校准占用；云台输入持续而底盘断则进一步查板间CAN发送/接收。单块调试器分次观察仅用于缩小范围，不能替代同一时刻的两端记录。

首轮反馈只需要拨杆位置、模式是否跳变、是否捕捉到接收年龄超100ms、固定小摇杆时通道是否被清零，以及电机动力是否开启。发现卡顿可回双下结束，不需要持续复现。

## 7. 新增对照：用户表示旧校准代码可正常运动

用户进一步说明“用老代码的校准代码就底盘就能正常运动”。这是优先级很高的版本对照线索。尚待明确用户只替换了校准函数、替换了相关文件还是下载整套旧云台固件；不将该描述自动等同于已经完成严格单变量对照。

更新排查重心：如果其他条件相同，旧版正常而新版异常，应首先查新旧改动及其运行参数差异。此前左下右中不读Yaw校准角的结论，只排除了直接角度计算路径，不能排除本次修改造成的间接影响。40ms发送/100ms超时为旧实现已有条件，单凭它不能解释新旧行为差异；即使后续发现超时，也仍需找新版为何更容易出现它。

本次所谓“小Yaw校准修改”实际涉及5个源/头文件，并非只改动作轴：校准流程/门控、Flash标记及加载、小Yaw机械中位与限位、电机反馈快照，以及CAN电机发送实现均有变化。CAN_receive.c旧版三个轴共用gimbal_can_send_data，更新本轴字节时保留其余历史字节；新版每帧从全零开始，只设置本轴字节，并保护邮箱提交。故“总线/ID/本轴字节位置没变”不等于“整个电机报文内容没变”，也不能由此断言该实现变化已导致底盘卡顿。

另一个间接路径是校准后实际参数改变：旧小Yaw固定1118，新小Yaw采用端点中位；普通大Yaw跟随函数虽然未改，输入的小Yawrelative_angle可能改变，从而产生不同跟随请求。该作用还取决于实际运行模式与大Yaw命令是否启用，当前已有外部注释大Yaw发送版本，不能无条件套用到所有版本。

不因新增对照擅自覆盖现有改动或恢复旧版共用发送缓冲；先明确用户实际切换范围，再选择匹配的新旧版本做离线差异归因。本轮仍未修改控制源码、编译烧录或要求连接车辆。
