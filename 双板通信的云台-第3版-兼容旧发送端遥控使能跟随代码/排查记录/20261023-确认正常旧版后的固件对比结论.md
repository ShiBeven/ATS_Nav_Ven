## 当前可以直接确认的发送冲突

当前 `Src/bsp_pid.c` 的TIM2偶数次回调中：

```c
CAN_cmd_gimbal_2(yaw_can_set_current);
CAN_cmd_gimbal(pitch_can_set_current);
CAN_cmd_gimbal_3(0);
```

当前 `application/gimbal_task.c` 控制循环末尾仍执行：

```c
CAN_cmd_gimbal_3(yaw2_can_set_current);
```

两处都向CAN1、ID0x2FF、字节4/5提交小Yaw命令。TIM2名义500Hz、隔次执行，约每4ms发送一次固定0；云台任务按1ms tick延时，正常控制时还会提交计算命令。输出因此由两处互相交替覆盖，并非完全禁用小Yaw，也不是只保留正常控制输出。

已在当前AXF反汇编中核实：

- HAL_TIM_PeriodElapsedCallback内：`MOVS r0,#0` 后调用 `CAN_cmd_gimbal_3`；
- gimbal_task内：读取小Yaw的最终给定值并调用同一发送函数。

正常旧固件和最初小Yaw校准固件的回调均没有该固定0发送。该冲突具有打断小Yaw控制指令、引入顿挫的机制；它对底盘的间接影响没有实测，不宣称已找到底盘根因。

如果固定0是为了临时禁用小Yaw，应该保证所有活动发送位置都遵从同一禁用意图；如果要正常控制小Yaw，应保留单一且一致的命令来源。由于本轮任务是查因、该修改来自外部调试，本轮没有擅自决定禁用还是恢复，也没有改动该文件。

## 其他明确的后续差异

- Pitch绝对角环Kp：正常旧版28，当前20；反汇编gimbal_init分别可见VMOV.F32 s2,#28与#20。它属于后续参数差异，不能说当前与旧版只有校准流程不同。

比较时保留指令、寄存器、立即数、命名对象和PC常量载入，仅规范化已知符号及函数内分支地址。这是所选序列对比，不是全程序等价证明，未验证运行时数据、时序、物理发送和供电。

CAN_CmdBoard3等函数的自动结果可显示不同，因为编译器使用的全局数组相对地址改变；“不同”标记需要人工解释，不能直接当成逻辑缺陷。源码中该函数体与正常备份一致。

正常40ms遥控转发与100ms底盘超时仍需区分：40ms是正常旧版也有的设置，不能单独解释旧正常新异常；新版本如果真的触发超时，还需要解释触发原因。

## 对首次校准改动的剩余排查范围

- 电机CAN帧旧版共用数组并保留其他字节，新版每帧清零只填本轴字节；提交增加一致性保护。三轴总线、ID及本轴字节位置相同，但完整载荷不同。没有总线证据时，不恢复旧共享缓冲，也不认定清零帧就是底盘故障来源。
- 小Yaw由固定1118参考改为端点中位，Pitch参考与限位也可能因重新校准改变；即使普通跟随函数未改，输入与实际受力可改变。大Yaw跟随还取决于运行模式及对应版本是否启用发送。
- Flash从旧GM标记改为G2P，门控会在没有有效新参数时保持云台无力。该门控未直接控制底盘模式3，但程序版本和已保存运行参数必须作为两项变量分别记录。

当前最合理的后续顺序是先固定版本，排除后续测试冲突，再针对首次校准修改做单项对照。不能把一次整套回退直接当作某一个校准函数已被证明有错。
