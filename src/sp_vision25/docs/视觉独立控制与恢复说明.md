# 视觉独立控制与恢复 Attack 门控

修改日期：2026-11-14。工作区：`/home/ats/ATS`。

## 1. 本次修改的目的

让 `auto_aim_debug_mpc` 的云台指令和射击请求不再等待行为树发送
`/decision/robot_mode = 1`。行为树、导航、串口节点和串口协议未修改。

配置文件 `src/sp_vision25/configs/standard3.yaml` 新增：

```yaml
require_attack_mode: false
```

这是启动时读取的开关，修改后需要重启视觉程序，不支持网页热切换。
配置缺少该项时默认使用 `true`，保留原有行为。

## 2. 两种模式的区别

| 项目 | `false`：当前独立控制 | `true`：原有行为树门控 |
| --- | --- | --- |
| 刚启动、尚未收到机器人模式 | MPC 有效时可以输出 | 等待 Attack 消息 |
| 收到 Move、Defend 或其他模式值 | 不改变视觉输出许可，不因模式变化归位 | 合法非 Attack 模式禁止持续视觉控制；非法值也禁止输出 |
| 云台指令发布条件 | `control` | `attack_mode_ && control` |
| 射击请求为 1 的条件 | `control && fire` | `attack_mode_ && control && fire` |
| 从 Attack 切换到非 Attack | 不因行为树模式变化归位 | 发布一次零角度归位和关闭射击 |
| 正常退出视觉程序 | 保留关闭射击与归位流程 | 保留原退出流程 |

`control`、`fire` 来自 MPC 规划结果；独立模式不强制它们为真。
没有有效控制结果时，不持续发布新的视觉云台追踪命令，射击请求为 0。
它不会主动清除下位机已经保存的角度，也没有新增目标丢失时的归位策略。

当前配置仍为 `auto_fire: true`。因此独立模式下，满足规划器开火条件时可以
直接发布 `/cmd_shoot = 1`，即使没有收到 Attack、比赛未开始或行为树发布 Move。
若只验证云台跟踪，应将正在使用的配置中的 `auto_fire` 设为 `false`，再重启视觉。

## 3. 为什么不只删除 send() 中的 Attack 判断

原来 `robotModeCallback()` 在收到非 Attack 模式后还会更改内部工作模式，
并在退出 Attack 时发布归位命令。只改 `send()` 仍可能让这些回调干扰视觉。

本次改法：

1. 构造函数接收 `require_attack_mode`，独立模式下将内部输出许可
   `attack_mode_` 初始化为 `true`。
2. 独立模式下 `robotModeCallback()` 直接返回，绕过模式切换、归位及相关警告。
3. 原来的 `send()` 判断保持不变：内部许可已开启，最终仍由 `control` 和 `fire`
   决定发布内容；原有退出处理也保留。

没有向 `/decision/robot_mode` 伪造或持续发布 Attack。这个内部许可不代表
行为树或下位机模式已经变为 Attack。

## 5. 编译、启动和检查

修改 C++ 后，只编译视觉包：

```bash
cd ~/ATS
source /opt/ros/humble/setup.bash
source ~/ATS/install/setup.bash
export HIKROBOT_SDK_ROOT=/opt/MVS

CMAKE_BUILD_PARALLEL_LEVEL=2 colcon build --packages-select sp_vision25 \
  --cmake-args -DCMAKE_BUILD_TYPE=Release
```

编译成功后，重启原来的一键启动流程：

```bash
cd ~/ATS
./NAV2.sh
```

已有导航运行时，只重启“ATS 视觉”终端中的视觉进程，避免再启动一套导航或串口。
也可在停止旧视觉后单独启动：

```bash
cd ~/ATS
source /opt/ros/humble/setup.bash
source ~/ATS/install/setup.bash
export HIKROBOT_SDK_ROOT=/opt/MVS

ros2 run sp_vision25 auto_aim_debug_mpc \
  ~/ATS/install/sp_vision25/share/sp_vision25/configs/standard3.yaml
```

独立模式的启动日志应包含：

```text
require_attack_mode=false (independent vision control)
```

网页仍为 `http://127.0.0.1:8090/`。

在已加载 ROS 环境的终端分别检查，每条持续监听命令单独占一个终端：

```bash
ros2 topic echo /cmd_gimbal
```

```bash
ros2 topic echo /cmd_gimbal_joint
```

```bash
ros2 topic echo /cmd_shoot
```

在 MPC 控制结果有效时，即使 `/decision/robot_mode` 不是 1，也应能看到
`/cmd_gimbal` 中 `source: 3` 的视觉输出。不要为了验证本开关而同时向
运行中的行为树模式话题反复发布消息。

## 6. 后期恢复方法

把视觉程序实际读取的 YAML 中这一项改回：

```yaml
require_attack_mode: true
```

重启视觉后应看到：

```text
require_attack_mode=true (follow decision/robot_mode)
```

恢复后：未收到 Attack 时不持续发布视觉追踪指令；收到 Attack 且 MPC 有效才输出；
退出 Attack 时保留原有归位与关闭射击行为。无需重写行为树，也无需改回 C++。

当前安装配置是源码配置的符号链接：

```text
install/sp_vision25/share/sp_vision25/configs/standard3.yaml
  -> src/sp_vision25/configs/standard3.yaml
```

因此当前工作区只改 YAML 并重启即可。其他工作区如果安装的是配置副本，
则还需重新安装视觉包，或直接修改实际加载的安装配置。以启动命令里的路径为准。

## 7. 修改的边界与电控验收

串口仍由 `standard_robot_pp_ros2` 唯一管理。视觉仍通过以下 ROS 链路提交命令：

```text
视觉 -> /cmd_gimbal -> gimbal_manager -> /cmd_gimbal_joint
     -> standard_robot_pp_ros2 -> USB -> 电控

视觉 -> /cmd_shoot -> standard_robot_pp_ros2 -> USB -> 电控
```

本次只解除视觉侧对行为树模式的依赖，不修改：

- 行为树的比赛开始、血量、弹量、地图有效性、姿态模式等判断；
- 行为树向下位机发布的实际机器人模式；
- `nav_hold` 与地图坐标转换逻辑；
- 串口数据包格式、字段映射和电控固件。

所以 `/cmd_gimbal` 有输出，只能证明视觉已提交指令，不能据此证明电控已经接受。
如果电控固件仍要求实际 Attack 模式才能接管云台，或者接收的是独立视觉协议包，
本次改动不会自动解除那些限制。当前整车串口路径也不会因此新增 MPC 速度、加速度字段。
应分别确认 ROS 指令、串口发送、下位机解析和执行。
